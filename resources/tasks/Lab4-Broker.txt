Laboratory Work 4: A Message Broker
Goal. Build a message broker: the program in the middle of many dis-
tributed systems. Publishers send messages to a topic; the broker puts
each one in a queue and delivers it, in the background, to every subscriber
of that topic. Publishers and subscribers never talk to each other, only to
the broker, so either side can stop, change or multiply without the other
noticing. The lab has two parts, defended separately, and one grade. In
Part 1 the broker speaks HTTP: a REST API with JSON, and it forwards
each message to the subscribers of its topic over an answer that stays
open. In Part 2 it speaks gRPC: the same broker and the same tasks,
with a contract in Protocol Buers and a stream for each subscriber.
Keywords: message broker · publish/subscribe · HTTP · REST ·
streaming · gRPC · Protocol Buers
1
The broker
A topic is a named channel: grades, news, orders. A publisher sends a message
to one topic; the broker gives it an id (1, 2, 3, . . . in each topic) and the time, and
keeps it. A subscriber of a topic gets the messages of that topic as they arrive,
in order, once (Fig. 1). Publishers and subscribers know only the address of the
broker: a publisher does not know who reads its messages, or whether anybody
does at that moment.

4.1
Task 1: Publish and deliver
Goal. The broker puts each message in a queue, and delivers it in the background
to the subscribers of its topic.
The broker answers the requests of Table 2, and the ids of a topic start
at 1 and grow by one. A publish does not wait for the subscribers: the broker
gives the message its id and time, puts it in a queue, and answers at once with
202 Accepted and the message. In the background, a delivery task takes the
messages out of the queue, in order, and writes each one to all the subscribers
of its topic (Fig. 2). The requests are the producers, and the delivery task is the
consumer, as in Lecture 3.
A subscriber subscribes with GET /topics/topic/stream. A subscriber that
is gone does not stop the delivery to the others: the broker forgets it when it can
no longer write to it.

4.2
Task 2: Restarts
Goal. Nothing is lost when the broker restarts.
The broker keeps the messages on disk: after a restart nothing is lost, and
the ids go on. A broker killed in the middle of a write must not lose a le: write
the new content to a temporary le, then put it in the place of the old one.
4.3
Task 3: Strangers
Goal. Only known publishers can publish.
Publishing needs a token, in the header Authorization: Bearer token. The
broker reads the tokens from a le, each with the name of its publisher and the
topics it may publish to. Without a token, or with an unknown one, a publish
gets 401 Unauthorized with WWW-Authenticate: Bearer; with a good token,
but to a topic that the token does not allow, it gets 403 Forbidden.

Part 2: The broker over gRPC
The architecture stays: the same topics, messages and ids, the same publishers
and subscribers, and the same three tasks. Nothing new to build: what changes
is how the programs talk. In Part 1 every program had to agree by hand on the
methods, the paths, the status codes and the elds of the JSON. In gRPC the
conversation is a contract, written in Protocol Buers: the .proto le names the
calls and the messages, and the code of the clients and of the server is generated
from it, in any language. A call looks like a method call, the data travels in
binary over HTTP/2, and a call can answer with a stream: the gRPC form of
the answer that stays open in Part 1 (Fig. 3).
 gRPC for everything: in this part the broker has no HTTP API.
 One .proto le, shared by all the programs, and code generated from it (in
C#: Grpc.Tools, with Google.Protobuf).
 The contract starts like this, with a call for each request of Table 2; the other
messages are yours to design.
syntax = "proto3";
package broker;
import "google/protobuf/timestamp.proto";
service Broker {
// one request, one answer
rpc Publish (PublishRequest) returns (PublishReply);
// one request, a stream of answers
rpc Subscribe (SubscribeRequest) returns (stream Message);
// the topics, and their sizes
rpc ListTopics (ListTopicsRequest) returns (ListTopicsReply);
}
message Message {
int64 id = 1;
string topic = 2;
string sender = 3;
string body = 4;
google.protobuf.Timestamp time = 5;
}
5.1
Task 1: Publish and deliver
Goal. The broker puts each message in a queue, and delivers it in the background
to the subscribers of its topic, over a stream.
Task 1 of Part 1, in gRPC. Publish puts the message in the queue and
answers at once with its id; Subscribe opens a stream, and the delivery, in the
background, writes into it every new message of its topic, for as long as the
stream is open; ListTopics answers with the topics and their sizes. A subscriber
that is gone does not stop the delivery to the others. The publisher and the
subscriber take the same parameters as in Part 1, and the subscriber shows the
messages in the same way.
